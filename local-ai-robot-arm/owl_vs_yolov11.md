# OWLv2 与 YOLOv11 对比文档

两个 Demo 用了完全不同类型的视觉检测模型。本文整理它们的核心区别、各自的
优缺点,以及为什么会出现这些差异。

---

## 一、核心区别一句话

- **OWLv2**:开放词汇(open-vocabulary)检测器。给一段文字描述,
  它就去图里找匹配的物体 —— 哪怕训练时没见过这个类别。
- **YOLOv11**:闭集(closed-set)检测器。只能识别训练过的固定类别;
  类别一旦定下来,模型就只会输出这些类。

这是**根本性**的不同,不是同一类工具的两个版本。

---

## 二、对比表

| 维度 | OWLv2 | YOLOv11 |
|---|---|---|
| 检测类型 | 开放词汇(文字 → 物体) | 闭集(类别 ID → 物体) |
| 是否需要训练 | 不需要,开箱即用 | 自定义类别需要标注+训练 |
| 推理速度 | 慢(MPS 上约 80–150ms) | 快(MPS 上约 5–15ms,可实时) |
| 模型大小 | ViT-Base ≈ 145M 参数 | YOLOv11n ≈ 2.6M;s≈9.4M;m≈20M |
| 准确率(熟悉物体) | 中等 | 训练好后通常更高、定位更紧 |
| 添加新物体 | 改一行文字 query 即可 | 需要重新标数据、重新训练 |
| 输出 | 文字 query 对应的框 | 类别 ID + 框 + 置信度 |
| 适合的硬件 | 偏向 GPU/MPS,CPU 太慢 | 边缘设备、CPU 也能跑 |
| 跨场景泛化 | 强(预训练数据极大) | 弱(只在训练集分布内) |

---

## 三、为什么差别这么大

### 1. 网络结构与训练目标

**OWLv2** 的核心是一个 **Vision Transformer(ViT)** 视觉编码器 + 一个文本
编码器(类似 CLIP)。训练时让大量"图像 + 文字描述"对在同一个语义空间
里对齐。推理时:

```
用户:"a green cube"
        ↓ 文本编码器
   query 向量
        ↓
   和图像中所有候选框的视觉向量做相似度匹配
        ↓
   相似度高的框 = 检测结果
```

正因为输入是文字向量而不是固定 ID,所以理论上**任何**能用文字描述的物体
都能查询。

**YOLOv11** 是经典的卷积/混合检测网络(ultralytics 的迭代),输出层是
固定的 N 个类别 logits。训练时每个类别都需要大量带框标注。推理时:

```
图像 → 检测网络 → [80 个类别的概率, 框的坐标]
```

类别和数量在训练时就**写死**在网络结构里。

### 2. 速度差异的来源

YOLOv11 的小版本(n / s)只有几 M 参数,主干是高度优化的卷积;OWLv2
是 ViT 主干 + 文本编码 + 跨模态注意力,计算量大一个数量级。Demo 里
OWLv2 单帧推理在 M2 Air 上约 100ms,YOLOv11s 可以做到 60+ FPS。

### 3. 准确率的取舍

如果只检测**已知**的几类(比如训练好的"绿色方块、蓝色方块、纸盒"):

- YOLOv11(训练充分):mAP 会比 OWLv2 高 5–15%,框更紧,误报少
- OWLv2:做"绿色方块"还可以,做"右上角那个磨损的方块"开始变弱

如果场景里出现**没训练过**的物体(比如临时让机器人拿信用卡):

- YOLOv11:完全不会识别 —— 必须先标 100 张信用卡图、重新训练
- OWLv2:把 query 改成 `"a credit card"` 就能用,不需要任何训练

## 四、两个 Demo 的实际差异

### 当前 OWLv2 Demo

```
语音 → Qwen3-1.7B 解析出 {action, object}
       ↓
   "object": "a green cube"  —— 这是自由文本
       ↓
   OWLv2(text query = "a green cube")→ 找到框
```

优点:语言模型可以让用户说**任意**物体名字,系统大体上都能去找。
没有"训练 → 部署"的循环。

缺点:慢(整套链路一次 1–2 秒),边界框不如 YOLO 紧,对小物体或复杂背景
容易漏报/误报。

### YOLOv11 Demo

```
图像 → YOLOv11 → ["green_cube" 框, "blue_cube" 框, "box" 框, ...]
                       ↓
       根据某种规则(比如最近、置信度最高)选目标
                       ↓
       机器人执行
```

优点:实时,准确,可在很弱的硬件上跑。

缺点:类别在训练时就固定了。要加"信用卡"必须重新采图、标注、训练。
如果做语音控制,LLM 输出的"object"必须**精确匹配**某个已训练类的名字
(或者做映射)。

## 五、什么场景选什么

| 场景 | 推荐 |
|---|---|
| 类别固定、追求速度、有 GPU 训练资源 | YOLOv11 |
| 类别经常变、用户随口指定物体、原型阶段 | OWLv2 |
| 在 Jetson Nano / Raspberry Pi 等边缘设备 | YOLOv11(尤其 n/s 版本) |
| 在 Mac / 笔记本上跑且接 LLM | OWLv2 |
| 比赛/展示要"自然语言指挥机器人" | OWLv2 |
| 工厂流水线、固定物料、要求 99% 召回 | YOLOv11(用自家数据训练) |
| 想加新物体但不想标数据 | OWLv2 |
| 同时需要快和广,可以两个一起用 | 见下文 |

---

## 六、两者能不能配合使用

可以,而且在生产里很常见的组合是:

1. **OWLv2 用于离线/低频"探索"** —— 给陌生物体打第一批伪标签
2. 把这些标签校验后用来 **fine-tune YOLOv11**
3. **YOLOv11 用于在线高速运行**

或者:

- 把 YOLOv11 用作"已知物体"的快速管道
- 当 LLM 解析出未在 YOLO 类别里的物体时,回退到 OWLv2

这样既保留速度,又保留语义灵活性。

## 七、当前 Demo 的具体技术差异(易踩坑)

| 项目 | OWLv2 写法 | YOLOv11 写法 |
|---|---|---|
| 模型加载 | `Owlv2Processor.from_pretrained(...)` | `YOLO("yolo11n.pt")` |
| 推理调用 | `processor(text=[queries], images=pil)` → `model(**inputs)` | `model(frame)` 直接返回 |
| 后处理 | `post_process_grounded_object_detection` 加阈值 | results 里直接有 `boxes / cls / conf` |
| 阈值 | OWL 一般 0.05–0.15,需要按场景调 | YOLO 一般 0.25–0.5,默认就好 |
| 颜色等细粒度区分 | 直接写在 query 里,如 `"a green cube"` | 必须把"green_cube / blue_cube"作为**不同类**训练 |
| 自定义类 | 不需要训练 | 需要数据集 + `yolo train` |
| 文本对齐错误 | "green cube" 误中蓝方块 → 加 query 消歧义 | 训练数据不够 → 加图重训 |

---

## 八、结论

- **OWLv2**:语义灵活,**适合接 LLM**,适合 demo 和原型。代价是慢、贵。
- **YOLOv11**:工程性强,**适合上产线/边缘**,代价是想加东西就得重训。

两者不是替代关系,而是**互补**。这次的两个 demo 正好展示了这两条技术
路线的极端 —— 一个用大模型走"语义匹配",一个用小模型走"分类训练"。
